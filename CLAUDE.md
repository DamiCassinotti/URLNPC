# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**URLNPC** is a Unity 6 LTS game project featuring a first-person combat arena where an AI enemy NPC is trained using Unity ML-Agents (reinforcement learning) to fight against the player.

## Build & Run

- **Play the game:** Open the project in **Unity 6000.0 LTS**, load `Assets/Scenes/FPS.unity`, press Play.
- **ML training:** Create a Python 3.10 venv, install `requirements.txt`, then drive training through `scripts/train.sh` (wraps `mlagents-learn`) from the repo root:
  ```bash
  python -m venv .venv && source .venv/bin/activate
  pip install -r requirements.txt
  scripts/train.sh editor <run-id> [config]   # press Play in the editor to feed it
  scripts/train.sh build  <run-id> [config]   # headless standalone build, live opponent
  ```
  `config` defaults to `config/URLNPC.yaml` (slice/full/self-play configs and the full walkthrough are in `docs/rl-runbook.md`). Trained models (`.onnx` files) are saved to `results/<run-id>/`.
- **Score a model:** `scripts/eval.sh results/<run-id>/URLNPC.onnx --episodes 100 --seed 1001 --opponent heuristic` — headless rounds, no trainer, summary in `results/eval/`. See "Headless evaluation" below.

## Tech Stack

- **Unity:** 6000.0 LTS
- **ML-Agents:** package `3.0.0` (Release 22), embedded at `Packages/com.unity.ml-agents/` and locally patched to use `Unity.InferenceEngine` instead of the deprecated `Unity.Sentis` namespace. Sentis was rebranded to "Inference Engine" (`com.unity.ai.inference`) in Unity 6, but ML-Agents 3.0.0 was authored against the old namespace — the embedded patch bridges that gap.
- **Inference Engine:** `com.unity.ai.inference` 2.6.1 (formerly Sentis)
- **Input System:** new (`com.unity.inputsystem`), legacy Input class disabled. Player controller is **Starter Assets — First Person Character Controller**, with Cinemachine driving the camera via a virtual camera following `PlayerCapsule/PlayerCameraRoot`.
- **Python (training):** 3.10.12, `mlagents 1.1.0`, `torch 2.2.1` — see `requirements.txt`.

## Architecture

### Component Relationships

**Game state** is managed by `GameManager.cs`, which tracks win/loss conditions, controls the end-of-round UI, and calls `CounterData` (static class) to persist scores across scene reloads. `GameManager` holds a generic `[SerializeField] Behaviour playerController` reference that is disabled at end-of-round — wire whichever player controller component you're using (currently StarterAssets `FirstPersonController`) to that slot in the Inspector.

**Round clock:** `GameManager` also runs a configurable round timer (`roundDurationSeconds`, default 120 s game time — it scales with the trainer's `time_scale`; ≤ 0 disables it). Timeout is a **draw**: no winner is forced and `CounterData.Draw()` records the outcome. In human play a draw ends the round exactly like a win — freeze, "Draw!" banner, and the end-of-round button reloads the scene into a completely new round (fresh arena, fresh spawns); agents are *not* reset in place on this path. During training (communicator on), every `EnemyAgent` instead gets `OnRoundTimeout()` (negative terminal reward `timeoutPenalty`, default `-0.6`, then `EndEpisode()`), the clock is rearmed and the scene keeps running — `EnemyAgent.OnEpisodeBegin` calls `GameManager.ResetRoundClock()` so every episode gets a full budget without a scene reload. **`EnemyAgent.Initialize` forces `Agent.MaxStep = 0`:** the round clock is the single owner of time-based episode termination. The binary FPS scene carries a stale serialized `MaxStep` of 5000 (~100 s, shorter than the round), which used to end episodes silently before the clock fired — timeouts restarted the round in place and draws were never counted. Remaining time is queryable via `GameManager.RemainingRoundTime` (the "tiempo restante" input for the future GameStateSnapshot/LLM context) and shown on a runtime-created HUD text (the scene is binary, so the label is built in code like the Reset Score button).

**Enemy AI** is split across three scripts:
- `EnemyAgent.cs` — the ML-Agents `Agent` subclass (the **only** `Agent` on the Enemy GameObject). Gathers the policy's inputs off `EnemyBehavior`/`PerceptionMemory`/`DamageMemory`/`ModeChannel` into an `NpcObservationInput`, hands it to `NpcObservations.Fill`, receives the two discrete action branches via `ActionBuffers` and assigns rewards. Subscribes to `Health.OnDamaged` / `OnDied` on both itself and the player target to emit hit/kill/death rewards. Calls `EndEpisode()` on either death and resets state in `OnEpisodeBegin()`.
- `EnemyBehavior.cs` — plain `MonoBehaviour`. Executes the actual behavior: `Move(MovementAction)` runs the movement primitive the policy picked, `Attack()` fires with cooldown, and it provides the observation primitives (`IsTargetInSight`, `ReadCanAttack`, etc.) plus `ResetState()` for episode resets.
- `PerceptionMemory.cs` — enforces the **sensory contract**: the NPC never knows the player's HP and knows their position only while visible (`CurrentlyVisible`, `LastSeenPosition`, `TimeSinceSeen`, updated from `IsTargetInSight()`). The memory has a horizon (`memorySeconds`, default 10 s = `NpcObservations.SeenHorizonSeconds`, so the staleness observation spans its whole range and then reads as the never-seen fixed point): a sighting older than that lapses back to never-seen, which is what turns "lost the player" into a search instead of a permanent aim point (#72). It is the *only* source of target info for the NPC brain — every movement primitive navigates relative to and `Attack()` aims at `LastSeenPosition` (firing is gated on `SeenWithin(CombatBalance.FiringGraceSeconds)`, 1 s, rather than `HasEverSeen` — long enough to suppress the corner the player just ducked behind, short enough that standing still shooting at a memory is not a strategy), and the `targetInSight` observation reads `CurrentlyVisible`. Environment code (spawn separation, reward computation like `DistanceToTarget()`, and the sight check itself) may still read true state; only policy inputs/actions are restricted. Auto-added at runtime by `EnemyBehavior.Awake` (binary prefab), memory wiped by `ResetState()` on episode begin.

**Brain interface (frozen, #43):** `NpcBrainSpec.cs` is the single declaration of the policy's shape — 18 observations, two discrete branches (7 movement primitives x 2 fire). The Enemy prefab's serialized `BehaviorParameters` and `CombatantRig`'s runtime-composed player both have to match it, so the rig reads the constants and the tests hold the prefab to them; the two sides share one behavior name, so a mismatch is a broken self-play run rather than a compile error. **`EnemyAgent.Awake` forces the shape onto whatever `BehaviorParameters` it finds**, the way `Initialize` forces `MaxStep`: the binary FPS scene is a *prefab instance* pinning the old 3-float, one-branch shape as an override, and no edit to `Enemy.prefab` reaches that. It has to be `Awake` and not `Initialize` — `Agent.OnEnable` builds the actuators off the action spec before `Initialize` runs, so a branch count fixed there lands too late (the observation size alone would survive, since sensors are built after). Changing any of it invalidates every trained model. The observation layout itself is the `NpcObservations` POCO (`Fill(float[], NpcObservationInput)`), slot by slot: 0 canAttack, 1 cooldown remaining, 2 target visible, 3 distance to the perceived position / `sightRange`, 4-5 bearing sin/cos vs own forward, 6 time since seen / 10 s, 7 own HP, 8 recently damaged, 9-12 hit-direction one-hot, 13-16 commanded-mode one-hot, 17 own speed — all normalized, and everything about the target read off `PerceptionMemory` alone. Never seen is a single fixed point (distance 1, staleness 1, no bearing) rather than whatever a zeroed last-seen position would imply. Both branches act every step: `OnActionReceived` runs the movement primitive, then fires, so `Attack()`'s aim is the last word on the facing. The fire branch's own choice gates the wasted-shot penalty — `EnemyBehavior.DidShoot` holds a stale `true` from the last step the trigger was pulled.

**Movement primitives:** the movement half of the action space is the `MovementAction` enum (`Hold`, `Advance`, `Retreat`, `StrafeLeft`, `StrafeRight`, `MoveToCover`, `Wander` — declaration order is the action index order, so changing it invalidates trained models), dispatched by `EnemyBehavior.Move`. Every destination is derived from `PerceptionMemory.LastSeenPosition`, never `target.position`. `Advance` heads for the remembered position itself, so the solver routes the whole way around whatever is in between — and once it arrives without reacquiring the target it latches into `Wander` (the latch clears on the next sighting or `ResetState()`), because standing on an empty spot is not pursuit and an unlatched check would bounce it between the spot and its first wander waypoint — a straight-line step instead picks waypoints on the far side of a building and works the doorway. `Retreat` and the strafes have no goal point, only a direction: they step one `moveStepDistance` (6 m) against or across the bearing, from an on-mesh-snapped origin (the Enemy prefab lifts the body a metre by its agent base offset, so `transform.position` is off the mesh), trimmed at the first NavMesh edge along the way so a step through a wall doesn't map onto the mesh on the other side — and skipped altogether when the agent already stands on that edge, since a zero-length destination just pins it there. Before the first sighting there is no bearing to move along, so `Advance`, `Retreat` and the strafes all fall through to `Wander`: running off own facing would bury the NPC nose-first in the first wall it meets, where it stops moving, stops turning and never sees anything to break out with. `Hold` is the exception — standing still is well defined with no target, so it faces its own way and holds. The strafes turn the `NavMeshAgent`'s `updateRotation` off and set the facing themselves, so the sidestep doesn't rotate the target out of the sight cone; every other primitive turns it back on, and so does `ResetState()`. `MoveToCover` asks `ArenaManager.NearestCoverPoint` with the perceived position as the threat and its own `SightObstacleMask` — the query wants the *threat's* mask, but a human player has no sight model to read, so the mover's stands in; the same thing while both sides keep the `~0` default — and falls back to `Retreat` when the layout offers no cover; the query raycasts and path-checks every cover box in the arena, so it re-runs at most every `coverQueryInterval` (0.25 s) and walks to the cached point in between. `Wander` is the search: with nobody in sight it is what every other moving primitive falls through to, so how much ground it covers is most of whether a round ends in a kill or a draw (#93). Its rules are the `SearchPlanner` POCO — a leg goes to the farthest of `searchCandidateCount` (4) arena-wide points, ones in a `cellSize` (8 m) patch already swept this episode scoring `sweptWeight` (0.35) of their distance, so consecutive legs pull into the unswept parts of the map. The old version hopped to a point within `walkPointRange` (10 m) of itself, i.e. a random walk, which in a 60×60 m arena times the round out before the two ever meet; the local jitter survives only as the fallback for a scene with a NavMesh and no `ArenaManager`. Candidates are drawn on `RunRng.Stream.Wander` (`ArenaManager.RandomGroundPoint(stream)`) — a policy-dependent number of draws on the spawn stream would move every later spawn. A leg is given up on when the body arrives, or when it hasn't got `progressEpsilon` (0.5 m) closer for `legTimeoutSeconds` (4 s). Closer along the *path*, not the straight line (`EnemyBehavior.RemainingToWaypoint` reads `NavMeshAgent.remainingDistance`, falling back to the straight line only when there is no path length to read, which is the stranded case): the arena is full of buildings, and a leg routed the long way around one holds its straight-line distance flat for seconds. For the same reason the first reading of a leg sets the bar rather than the straight line it was picked on. That timer counts driven time, not wall time: each call charges the gap since the last one capped at `maxTickSeconds` (0.5 s), so a stretch where another primitive was at the wheel can't expire a leg that was never attempted, while a leg the policy only comes back to every few steps still expires eventually — being stranded is the case the timeout is for. The five numbers are `[SerializeField]` on `EnemyBehavior` and wired onto the POCO in `Awake`, the way `EnemyAgent` wires `EpisodeProgress`. Since the policy picks a primitive per decision step, a half-walked leg is routinely interrupted by one that clears the path (`Hold`) or overwrites the destination (`Retreat`, the strafes), so a `Wander` step that isn't re-picking re-issues its own destination instead of standing still until the timeout. `EnemyBehavior.Move` marks the current patch swept under *every* primitive, not just `Wander`, and `ResetState()` clears the sweep. All seven are reachable: branch 0 of the frozen action space is the primitive index.

**Commanded mode:** the NPC brain is mode-conditioned — one shared policy whose behavior depends on a commanded `NpcMode` (`Hunt`, `HoldCover`, `Retreat`, `Patrol`; the declaration order is the one-hot order, so changing it invalidates trained models). `ModeChannel.cs` is the slot holding it (`CurrentMode`, `TimeInMode`, `SetMode`, `ModeChanged(previous, current)` — raised once per mode *interval*: re-commanding the same mode mid-episode is a no-op, so listeners aren't flooded with one event per decision step and `TimeInMode` keeps running, while an episode reset always starts a fresh interval and announces it, reporting `previous == current` when the same mode is redrawn. A listener segmenting the timeline off the events therefore never disagrees with `TimeInMode`). Exactly one writer at a time: `ModeDirector.cs` during training, the LLM selector at inference — nothing arbitrates between them, so the director carries a `trainingOnly` flag (default on) that stands it down unless the trainer's communicator is attached; untick it to run the scripted schedule as the random-mode evaluation baseline, or for manual inspection with `forcedMode`. The director draws from `ActiveModes`, which is code-owned during training and the serialized `enabledModes` mask (`NpcModeMask`) outside it (#82): `NpcModes.ResolveEnabled` returns all four modes whenever the trainer's communicator is on — unless `-trainModes <all|Mode[,Mode...]>` narrows the pool for a restricted-pool run (#97), one process-wide argument that reaches both self-play bodies where three serialized masks could not — the way `CombatBalance` owns the combat numbers — `Enemy.prefab`, a scene instance override and `CombatantRig`'s composed director are three separate serialized masks, and the two self-play bodies could otherwise train on different pools. Outside training the Inspector field wins, so manual play and the mode baselines can still pin a subset. It draws every `minDwellSeconds` (default 5 s, near the LLM selector's decision period, so the policy trains on the switch rate it meets at inference) on `RunRng.Stream.Mode`. It ticks in `FixedUpdate`, the step the agent's decisions run on, so a seeded run replays the switch *times* and not merely the drawn sequence — off `Time.time` in `Update` the switches quantise to whatever frame rate the editor or a headless build hits. A draw may repeat the current mode and simply extends the dwell — forbidding repeats would make a two-mode pool alternate deterministically. `useForcedMode`/`forcedMode` pins one mode for manual inspection. `ModeDirector.ResetState()` (called by `EnemyAgent.OnEpisodeBegin` on its own body's director, when there is one) draws immediately rather than arming the next tick, and forces the write via `ModeChannel.ResetState` — the agent collects its first observation on the Academy step, and a redraw of the mode the last episode ended on would otherwise be dropped as a no-op with `TimeInMode` still counting the old dwell. The sampling rules are the `ModeSchedule` POCO (both "now" and the draw injected); the MonoBehaviour is the adapter. `EnemyBehavior.Awake` finds-or-adds the director alongside the channel and the memories (`PerceptionMemory`/`DamageMemory`), so every AI body — the enemy and `CombatantRig`'s agent-driven player — carries one and both sides of a self-play run command modes instead of training the shared policy stuck on `initialMode`; `Enemy.prefab` still ships a serialized instance for Inspector tuning, which the find-or-add picks up when present. The director stands down outside training (`trainingOnly`), so on a human-play or inference body the channel just reports `initialMode` until the LLM selector commands one. The other consumers are the per-mode reward columns (see "Reward shape") and mode compliance (see "Mode compliance").

- `DamageMemory.cs` — the "I was just shot, roughly from there" half of the brain's inputs, the counterpart to `PerceptionMemory` for the NPC's own body: it listens to `Health.OnDamaged` and keeps `RecentlyDamaged` true for `memorySeconds` (default 2 s) along with `LastHitDirection`, the shot bucketed to `HitDirection.Front/Back/Left/Right` relative to own forward at the moment of the hit (the body turns while the memory decays, so the bucket is taken once and kept). Damage with no known shooter still raises the flag but reports `None`, as does a lapsed memory — the flag and the direction can never disagree. The rules are the `DamageState` POCO; the MonoBehaviour is the adapter. Auto-added at runtime by `EnemyBehavior.Awake` and wiped by `ResetState()`, same as `PerceptionMemory`. Feeds observations 8–12.

`Health.cs` exposes `OnDamaged(DamageInfo)` and `OnDied` events that `EnemyAgent` listens to for reward shaping. `DamageInfo` carries the amount plus the shooter's ray origin — `Weapon` threads it through `DecreaseHealth`; the `DecreaseHealth(float)` overload is damage with no known source and leaves `HasSource` false rather than pointing at the world origin. `GameManager.ProcessDeath` early-exits when `Academy.Instance.IsCommunicatorOn` so it doesn't freeze the scene during training.

**Weapons** use a raycast-based hit system defined in abstract class `Weapon.cs`, with `PlayerWeapon.cs` (new Input System: `Mouse.current.leftButton.wasPressedThisFrame`) and `EnemyWeapon.cs` (called by `EnemyBehavior`) as concrete implementations. Hits call `Health.DecreaseHealth()` on the target.

**Body origins (#103):** the two combatant bodies don't share one. `Enemy.prefab`'s transform sits at its capsule centre and its `NavMeshAgent` base offset (1 m) lifts it onto the mesh; `CombatantRig`'s player body is the StarterAssets capsule, origin at the feet, offset 0. `BodyMetrics` is the one place that reconciles them — `MuzzleOffset` (mid-body, what `EnemyWeapon.GetPosition` fires from) and `EyeOffset` (the head cover has to hide). Both land at the same world height on either body, and on the Enemy prefab the muzzle offset works out to 0, so the NPC's shots leave exactly where they always did. Reading `transform.position` raw is what had the agent-driven player firing from ankle height (0.08 m against the NPC's 1.08) and losing 90% of self-play rounds. The same asymmetry applied to the *threat's* eye: `EnemyBehavior.IsHiddenFromTarget` and the `NearestCoverPoint` call in `MoveToCover` take the target's own base offset out of `target.position` / `PerceptionMemory.LastSeenPosition` (`EnemyBehavior.TargetBaseOffset`, read off the target's `NavMeshAgent`, 0 for a human body) rather than the asker's. `IsTargetInSight` goes through the same helper but at **muzzle** height on both ends, not eye height: `Attack` turns the body at the target and fires horizontally from the muzzle, so a sight ray any higher would report a sighting over a wall the bullet goes straight into. Sight is the shot's own line; the cover probes are the head's.

**Combat balance (#71, #73):** `CombatBalance.cs` owns per-shot damage (15, i.e. 7 hits through 100 HP), the NPC fire cooldown (0.5 s), its aim spread (1.5°), how long after losing sight it may still fire (`FiringGraceSeconds`, 1 s — #72) and its sight range (45 m — the arenas run to 60×60 m and spawns are 25 m apart minimum, so the old 20 m had the NPC starting every round blind; it is also observation 3's normalization scale, so a change invalidates trained models). It has to be code and not the Inspector: the FPS scene's Enemy is a **prefab instance** whose serialized overrides pin `attackCooldown: 1` and `damage: 12` — an edit to `Enemy.prefab` never reaches an instance override, and the player's weapon is authored straight into the binary scene where nothing reaches it — so `Weapon.Awake`, `EnemyWeapon.Awake` and `EnemyBehavior.Awake` force the values on, the way `EnemyAgent` forces `MaxStep`. The `[SerializeField]` fields stay (renaming them would drop other scene overrides) but are ignored at runtime; tune the constants instead. Both sides read them, so `CombatantRig`'s runtime-composed player fights the same weapon the enemy does. Changing them changes what the RL rewards pay for — retrain after.

**Health & death:** `Health.cs` tracks HP for both Player and NPC. On death it calls `GameManager.ProcessDeath()`, which reads the entity's tag (`"Player"` or `"NPC"`) to determine the winner.

**Arenas:** `ArenaManager.cs` procedurally builds the level at runtime. Because the scene is force-binary serialized, level geometry is generated in code rather than authored in the scene. On `Awake` (it runs at `[DefaultExecutionOrder(-10000)]` so the NavMesh exists before the enemy spawns) it destroys any static `Arena` root, picks 1 of 5 layouts (random, or `forcedArenaIndex`), builds floor/walls/cover from primitive cubes with contrasting URP/Lit materials, and bakes a fresh NavMesh via a runtime `NavMeshSurface` (`Unity.AI.Navigation`). It exposes `ArenaManager.Current` so `EnemyBehavior.GetRandomPositionInMap` samples spawn points from the active arena's NavMesh instead of hard-coded ±60 bounds, and repositions the player to a **random** NavMesh point on `Start` (seeded via `RunRng`, every round, all modes). The auto-bootstrap re-checks on **every** scene load (`SceneManager.sceneLoaded`), not just the first: the manager and its generated arena die with each `LoadScene`, and without the re-check rounds 2+ had no manager — no arena re-roll, and the old static `Arena` root baked into the scene was left standing. Placing the component in the scene still works and takes precedence. `RandomGroundPoint` also keeps spawns off the geometry (`IsClearOfCover`, `SpawnCoverClearance` 0.9 m from every registered cover box): being on the NavMesh isn't enough, because the bake insets the mesh only around what an agent *can't* step over — a point on a stair step or hard against a crate is on-mesh and still puts the capsule inside the box. When no clear point turns up it falls back to a crowded one, then an elevated one, rather than an off-mesh origin. See "Arenas" in `README.md`.

**Reproducibility:** `RunRng.cs` is a static, process-wide seedable RNG that all evaluation-relevant randomness routes through — arena selection, spawn-point sampling (`ArenaManager.RandomGroundPoint`, `EnemyBehavior` fallback), patrol/wander waypoints, commanded-mode sampling (`ModeDirector`) and the random-action control policy (`eval.sh --subject random`) — each on an independent sub-stream so a variable number of draws in one domain can't shift the others. Seed priority: `-runSeed <int>` command-line arg > non-zero `runSeed` Inspector field on `ArenaManager` > time-derived random (still logged, so any run is replayable after the fact). The seed is logged at startup (`[RunRng]` line) and recorded per episode as the `Run/Seed` stat in TensorBoard. `EnemyWeapon` aim spread deliberately stays on `UnityEngine.Random`: it's drawn a policy-dependent number of times, so routing it through the deterministic streams would desynchronise them between runs.

**Player drivers:** `CombatantRig.cs` (on the player body, auto-attached at runtime if absent) makes the player side swappable between a **Human** driver (the StarterAssets controller + `PlayerWeapon` authored in the scene — Human mode touches nothing) and an **Agent** driver, which disables all input-driven components (`FirstPersonController`, `StarterAssetsInputs`, `PlayerInput`, `PlayerWeapon`, `CharacterController`) and runtime-composes the enemy combat stack onto the body: `NavMeshAgent` + `EnemyWeapon` + `EnemyBehavior` (with `targetTag = "NPC"`) + configured `BehaviorParameters` + `PlayerAgent` (an `EnemyAgent` subclass) + `DecisionRequester`. Selection priority: `-playerDriver <human|agent>` CLI arg > `CombatantRig.DriverOverride` (static, settable from code) > Inspector field (default Human). `EnemyBehavior.targetTag` generalizes the old hard-coded `"Player"` tag so the same script hunts either side. `Health`, tags, and `GameManager.ProcessDeath` are driver-agnostic. The agent driver defaults to behavior name `URLNPC` / team id 1, i.e. shared policy with the enemy for self-play; give it a different name to train a separate player policy. The auto-attach re-runs on **every** scene load (`SceneManager.sceneLoaded`), like `ArenaManager`'s: the rig dies with each `LoadScene`, so an eval's rounds 2+ used to come back with the authored Human driver — inert in headless batchmode, which is how the opponent ended up firing ~6 shots per 200 episodes (#107). Training never saw it, since episodes reset in place. The bootstrap pulls `ArenaManager.EnsureExists()` up first rather than trusting the order of two `sceneLoaded` handlers: the composed `NavMeshAgent` needs the arena's fresh bake.

**Heuristic training opponent (#109):** pure self-play converged on two mutually weak agents — selfplay-02 scored ~50/50 against itself but lost ~2:1 to the scripted hunt-and-shoot heuristic in every mode, Hunt included, since neither side was ever aggressive enough to teach the other to punish aggression. `-heuristicOpponent <0..1>` (`scripts/train.sh build --heuristic-opponent F`, default 0) puts the **player** side — the opponent; the enemy is the side the eval scores — on `BehaviorType.HeuristicOnly` for that share of the training episodes, so the policy also has a competent aggressor to beat. `PlayerAgent` is the adapter (it, not `EnemyAgent`, so the enemy is never the one swapped) and the cadence is the `OpponentSchedule` POCO: an evenly spread share rather than a draw, since a policy-dependent number of draws would have to stay off the `RunRng` streams the arena and spawns share, and an exact cadence makes two runs at the same fraction comparable. The swap happens in `OnEpisodeBegin` and never mid-episode — `BehaviorParameters.BehaviorType`'s setter disposes the live policy, and by then the ended episode's terminal experience is already sent. A heuristic episode trains the enemy alone: a `HeuristicPolicy` body sends the trainer nothing. It is gated on the communicator, because outside training nothing learns from that body and `EvalSession` picks each side's policy itself. `Run/HeuristicOpponent` (0/1 per episode) reports the realized fraction in TensorBoard; the result is read off `eval.sh --opponent heuristic`, ELO being self-referential.

**Telemetry:** `TelemetryLogger.cs` is a self-bootstrapping, `DontDestroyOnLoad` singleton that writes one JSON line per event to `persistentDataPath/Telemetry/session_<utc>_<pid>.jsonl` (path is logged to the console at startup). It subscribes to `Health.OnDamaged`/`OnDied` (resubscribing on every scene load), the static `Weapon.ShotFired` event (weapon, victim-or-null, damage — fired once per shot, **before** the damage is applied, so the killing shot still belongs to the episode it decided) and the static `GameManager.RoundEnded` event (winner tag, or `GameManager.DrawResult` on a timeout; fired from both `ProcessDeath` and `ProcessTimeout`, before the training early-returns, so training rounds and draws are reported too). Emits `session_start`, `shot`, `damage`, `death`, `episode_summary` (winner, duration, per-side damage dealt/taken, shots, hits, accuracy) and `session_end`. Episode bookkeeping is the `EpisodeLog` POCO and line formatting is `JsonLine` (invariant-culture numbers, escaping that keeps a value from splitting a line); the MonoBehaviour is the Unity adapter. `RoundEnded` opens the next episode immediately (training has no scene reload); the reload that follows a human-played round is recognised and does not burn a second episode index. A failed write disables telemetry for the session rather than throwing — the write runs inside `Health.OnDied`'s listener chain, where an exception would skip `ProcessDeath` and wedge the round. Future systems (LLM decisions) emit through the public `LogEvent(type, fields...)`, as `EnemyAgent` already does for `mode_change` and `mode_compliance`. File-IO only — works in `-batchmode`.

**Mode compliance (#45):** the fraction of decision steps under each commanded mode that did what the mode asks — Hunt closes distance, lands a shot, or holds without backing off within `huntEngagementDistance` (20 m) of a visible target, Retreat opens distance or keeps the target's eye-line broken, HoldCover keeps the target's eye-line broken, Patrol walks through ground it hasn't covered yet. **Hunt and Retreat credit more than movement (#91):** the fire cooldown (0.5 s) is five decision periods long, so a hunter that has closed and is trading shots is neither closing nor firing on four steps in five and Hunt could not clear ~20% however well it fought; and a retreat that reached cover has broken contact whether or not it kept walking. Both rules had the eval's fight quality against them — #52 scored 88% wins and 72% accuracy on a policy reading 9% Hunt and 0% Retreat. The rules and the per-episode tally are the `ModeComplianceTracker` POCO; `EnemyAgent` feeds it one `ComplianceSample` per `OnActionReceived`, built from the same true-state reads the reward columns use, and flushes it on every terminal path (`EndEpisodeWith`) to `StatsRecorder.Add("Compliance/<Mode>", rate)` and to a `mode_compliance` telemetry line (steps/eligible/compliant/rate per mode the episode actually ran). **The denominator is eligible steps, not all of them (#88):** `ModeComplianceTracker.Eligible` calls a step eligible for Hunt only while the target is visible — there is nothing to close on otherwise — for Retreat while the target is visible or was seen within `contactSeconds` (3 s), i.e. while there is contact to break (cover is what a retreat aims for and cover ends visibility, so a visible-only denominator would make the cover credit unreachable), for HoldCover over the same window but PerceptionMemory's whole horizon long (`coverContactSeconds`, 10 s — cover is cover with respect to a threat you know is out there, and holding it is worth credit for as long as you do), and always for Patrol, which needs no target. Scored over every step the rate mostly measured how often the fight was joined, which is why the #85 reward bumps didn't move it. The raw step count is kept alongside, and a mode with no eligible step reports its steps with no `Compliance/<Mode>` stat at all rather than a zero that would drag the average back down. Two more details the numbers depend on: the closing rules use a small deadband so per-step jitter is neither closing nor opening, and the same deadband is what makes a Patrol step count as movement. **Three of the four rules failed to separate a random walk from the heuristic bot (#105)**, which is the test they exist to pass — random read Hunt 76% / HoldCover 70% / Patrol 0.4% against the bot's 99% / 63% / 0.6%. What each was actually measuring: Hunt's holding credit paid for any step in range of a visible target, so half a random walk's steps qualified; HoldCover scored over every step measured the arena's ambient occlusion, the target being unseen ~90% of a round; and Patrol scoring only the step that crossed into a fresh cell had a ceiling near 6%, since a body spends ~17 steps crossing one. Hence the narrowed holding credit, the contact window on HoldCover, and Patrol counting every step *inside* a patch that was fresh on entry (`EpisodeProgress.InNewArea`) provided the body actually moved. `--subject flee` is the positive control the cover rules needed. **Target-in-sight fraction (#87):** the same flush also reports, per mode, the share of those steps `PerceptionMemory.CurrentlyVisible` was true on — `StatsRecorder.Add("Visible/<Mode>", rate)` and a `visible` object on the same `mode_compliance` line. It is what says how much of the episode Hunt's and Retreat's rates were scored on, and it is where a mode that never engaged shows up now that compliance stays silent for one. Both rows are the `ModeTally` POCO (`ModeComplianceTracker` is the rules plus one of them; the tally counts steps, eligible steps and hits, and a hit on an ineligible step is dropped so the count can't exceed its denominator), fed in lockstep from `OnActionReceived`, so their step counts always agree. Flushing happens *before* the round ends — `GameManager.ProcessTimeout` notifies the agents ahead of `RoundEnded` for that reason, since `RoundEnded` is what moves the telemetry log on to the next episode (a death already runs in that order). `EnemyAgent` also logs a `mode_change` line off `ModeChannel.ModeChanged`, the timeline the offline behavior analysis segments on; it subscribes from the agent rather than a scan in `TelemetryLogger` because the channel is added at runtime and a scene-load-time scan can miss it — and from `Awake`, finding-or-adding the channel the way `EnemyBehavior` does, because component order decides which of the two runs first and `Initialize` can land after a writer's first command.

Because the builder knows where every cover box is, `ArenaManager` also exposes `NearestCoverPoint(Vector3 from, Vector3 breakLosFrom, LayerMask sightObstacleMask, out Vector3 coverPoint)` (for the upcoming MoveToCover action primitive): it registers all LOS-blocking boxes at build time (everything except the floor and perimeter walls), and for each computes the point one stand-off behind the object's far side from the threat, keeping the nearest candidate that (a) sits on the NavMesh, (b) has the threat's eye-line to it blocked (through `EyeLine.Blocked`, the probe `EnemyBehavior.IsHiddenFromTarget` shares, at the caller's eye height and ignoring the asker's own body — low geometry like stair steps self-rejects), and (c) is reachable via a complete NavMesh path from `from`. The mask is the caller's to supply and must be the threat's own (`EnemyBehavior.SightObstacleMask`), or the query calls a point hidden that the threat sees straight through. Returns `false` when the current layout offers no valid cover — callers must handle that (fall back to Retreat).

**Headless evaluation (#52):** `scripts/eval.sh <model.onnx> [--episodes N] [--seed S] [--subject policy|heuristic|random|flee] [--opponent policy|heuristic] [--modes scripted|none|<Mode>] [--time-scale F]` scores a trained policy over N rounds against the standalone build with no trainer attached, then runs `scripts/eval_summary.py` over the run's telemetry JSONL (win/loss/draw, damage dealt and taken, accuracy, time to kill, survival time, per-mode compliance/visibility/step counts, pooled over steps). Output goes to `results/eval/<...>/`. The runtime half is `EvalSession.cs`, a self-bootstrapping `DontDestroyOnLoad` adapter that is inert unless `-evalEpisodes` is on the command line; the argument parsing is the `EvalSettings` POCO. It applies the model with `Agent.SetModel` plus `BehaviorType.InferenceOnly` (`Default` would silently fall back to the heuristic if the model were missing, scoring the baseline while claiming to score the policy), sets the far side to `HeuristicOnly` for `--opponent heuristic`, puts the *scored* side on a control instead of the model for `--subject heuristic|random|flee` (#97, #105 — the kind sets `EnemyAgent.control`, which is what `Heuristic` plays: `random` draws uniformly over the two branches off `RunRng.Stream.Action`, `flee` runs `ScriptedRetreatPolicy` — back off in sight, take cover out of it, never fire — the positive control the Retreat and HoldCover rules are calibrated against; only the subject runs a control, a random or fleeing far side being a weaker opponent rather than a condition anything is scored against), points `ModeDirector` at the requested selector (nothing writes the channel outside training otherwise), counts `GameManager.RoundEnded`, reloads the scene for the next round and quits a frame after the last one — a frame, so the telemetry listener has written the final `episode_summary`. The clock is `Time.captureDeltaTime`, not `timeScale`: a round then covers the same number of decisions whatever frame rate the machine hits, and frames aren't throttled to real time, so an eval runs much faster than the fight it simulates. A seed still doesn't replay a run — aim spread is deliberately unseeded — so the numbers are an average over episodes. `GameManager.ProcessTimeout` notifies the agents when an eval session is active as well as during training, so a draw still flushes its compliance tally. **The model is baked into the build:** Inference Engine only imports ONNX in the editor, so `eval.sh` copies the file to `Assets/Resources/EvalModels/eval.onnx` (gitignored) and rebuilds the player whenever its hash changes.

**UI:** `Counter.cs` reads from static `CounterData` each frame to display win counts. TextMesh Pro is used for all UI text.

## Required Enemy prefab components

The Enemy GameObject **must** carry `BehaviorParameters` + `DecisionRequester` for ML-Agents to drive it at all — without a `DecisionRequester` no decisions are requested, `OnActionReceived` never fires, and the enemy stands still in every mode (heuristic, inference, and training). Both are present on `Assets/Prefabs/Characters/Enemy.prefab` (Behavior Name `URLNPC`, vector obs size 18, discrete branches 7 x 2, decision period 5, Behavior Type Default, no model assigned). The prefab is text-serialized YAML (only the scene is force-binary), so it can be edited directly. It carries **no** `RayPerceptionSensor3D`: the one it used to have fed the policy live target detections outside `PerceptionMemory` and outside the declared observation width, and would have given the agent-driven player a different observation shape under the same behavior name. Don't add one back.

## Reward shape (in `EnemyAgent.cs`, all serialized for Inspector tweaking)

Global rows — the commanded mode doesn't move them:

- `aliveRewardPerStep` `+0.0002`
- `killTargetReward` `+1.0` (ends episode)
- `diedPenalty` `-1.0` (ends episode)
- `wastedShotPenalty` `-0.05` (fire branch put a bullet downrange while the target was not in sight)
- `timeoutPenalty` `-0.6` (round clock ran out — draw, ends episode)
- `tooCloseDistance` `6 m` — the radius the per-mode `tooClosePenaltyByMode` column below applies inside (the distance itself is global; only the penalty varies)

**Per-mode columns (#44):** the mode in the `ModeChannel` selects which column is live, so the one-hot the policy observes actually changes what pays. Serialized as one `float[]` row per event, indexed in `NpcModes.All` order (Hunt, HoldCover, Retreat, Patrol); a row shorter than that falls back to the global `hitTargetReward`/`gotHitPenalty`/`tooClosePenaltyPerStep` (or to 0 for the rows with no global counterpart), so an Inspector edit can't throw mid-episode. Those scalars keep their names — the binary FPS scene may carry overrides a rename would silently drop.

| event | Hunt | HoldCover | Retreat | Patrol |
|---|---|---|---|---|
| `hitTargetRewardByMode` | +0.5 | +0.5 | +0.1 | +0.1 |
| `gotHitPenaltyByMode` | -0.3 | -0.6 | -0.6 | -0.5 |
| `closingRewardPerMeterByMode` (#85) | +0.03 | 0 | -0.03 | 0 |
| `coverRewardPerStepByMode` | 0 | +0.005 | +0.002 | 0 |
| `newAreaRewardByMode` (#85) | 0 | 0 | 0 | +0.01 |
| `tooClosePenaltyByMode` (#80) | 0 | -0.004 | -0.008 | -0.002 |

Hunt's too-close column is 0 on purpose: as one global row the penalty taxed the one mode whose job is to close, which is part of why Hunt wouldn't engage (#79).

The closing and new-area columns are 3x and 5x their first values (#85): at the old weights the first 4-mode run left Retreat and Patrol compliance near zero (0.015 and 0.005), the positional signal losing to default aggression and to having no reason to roam. HoldCover and `killTargetReward` were held fixed as controls so the lift stays attributable to these two rows.

The columns are the `ModeRewardTable` POCO; `RewardComputer.StepReward` takes a `StepRewardInput` (mode, fire/sight flags, distance, closing delta, cover and new-area flags), with `tooCloseDistance` the one positional scalar that stays global, and the agent reads the same table for the hit/got-hit `Health` events. The two positional inputs come from `EpisodeProgress`: metres closed on the target since the last step (capped, so a respawn or a NavMesh warp isn't progress) and whether this step entered a `newAreaCellSize` patch of the arena not visited yet — both reset on episode begin. The cover flag is `EnemyBehavior.IsHiddenFromTarget()`, an environment-side true-state read like `DistanceToTarget()`: it probes the *target's* eye-line to this body through the shared `EyeLine.Blocked` helper at the same eye height `MoveToCover`'s cover query uses, so the point the policy is sent to is a point the column pays for. `IsTargetInSight` can't answer it — being FOV-limited it would call "in cover" every step the NPC looked away. The probe is a raycast, so the agent only fires it for modes whose column is non-zero (`RewardComputer.RewardsCover`).

## Tests

Unity Test Framework suite in `Assets/Tests/` (EditMode = pure logic, PlayMode = integration with real geometry/NavMesh/Academy). Engine-free logic lives in POCOs — `RoundClock` (GameManager's countdown), `RewardComputer` (EnemyAgent's per-step decision reward, built from the agent's serialized tunables in `Initialize`), `PerceptionState` (PerceptionMemory's remember/freeze state machine, time injected as a value), `EpisodeLog` + `JsonLine` (TelemetryLogger's episode bookkeeping and JSONL formatting), `ModeSchedule` (ModeDirector's dwell/draw rules), `DamageState` (DamageMemory's decay timer and hit-direction bucketing), `NpcObservations` (the frozen 18-float observation layout), `ModeRewardTable` + `EpisodeProgress` (the per-mode reward columns and the closing-distance, new-area and distance-moved bookkeeping they read), `ModeTally` + `ModeComplianceTracker` (the per-mode step counter, and the compliance rules on top of it), `EvalSettings` (the eval run's command-line arguments), `CommandLineArgs` (the shared launch-argument scan behind `-runSeed`, `-playerDriver`, `-trainModes` and `-heuristicOpponent`), `RandomActionPolicy` + `ScriptedRetreatPolicy` (the `--subject random` and `--subject flee` controls), `OpponentSchedule` (which training episodes put the opponent on the scripted heuristic), `SearchPlanner` (Wander's sweep and leg-timeout rules, sharing `GridCell`'s floor-patch packing with `EpisodeProgress`), `BodyMetrics` (the muzzle and eye heights the two body origins are reconciled through) — each exhaustively covered in EditMode; the MonoBehaviours are thin adapters feeding them `Time`, raycast results and actions. Keep new game rules in this shape: pure class + adapter. The reward/config values stay as `[SerializeField]` fields on the MonoBehaviours — do not fold them into the POCOs or a nested serializable class, the binary FPS scene may carry serialized overrides that a field rename/move would silently drop. Run headless with `scripts/run-tests.sh [editmode|playmode|all]` (editor must be closed — single instance per project; results in `results/tests/`), or in-editor via the Test Runner window. CI (`.github/workflows/tests.yml`) runs both suites per PR through GameCI's `unity-test-runner`; it needs the `UNITY_LICENSE`/`UNITY_EMAIL`/`UNITY_PASSWORD` repo secrets and filters to the two `URLNPC.Tests.*` assemblies (the embedded ML-Agents package tests are deliberately excluded). **Never pass `-runSeed` to the test process** — it outranks the inspector seeds the reproducibility tests set on purpose (the tests `Assert.Ignore` where that would invalidate them).

## Known follow-ups

- **NavMesh bake** — now handled at runtime: `ArenaManager` bakes a `NavMeshSurface` over the generated arena on `Awake`, so no hand-baked NavMesh is required. (A hand-baked NavMesh in the scene is removed at startup.)
- **Player position reset on episode begin** — handled: during training (`Academy.Instance.IsCommunicatorOn`), `EnemyAgent.OnEpisodeBegin` teleports the player to a random NavMesh point (`ArenaManager.RepositionPlayerAtRandomPoint`) *before* the enemy respawns, so `EnemyBehavior.InitAtRandomPosition`'s min-spawn-separation check measures against the player's fresh position. Toggle via `repositionPlayerOnEpisodeBegin` on `EnemyAgent`. In human play the randomizer runs at round start instead: each scene reload, `ArenaManager.Start` places the player at a random NavMesh point (not per episode-begin, which would also fire on mid-round `MaxStep` resets and teleport a live player mid-fight).
